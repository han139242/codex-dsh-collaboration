# 项目对标

影响选型、主要功能、架构或常用任务时，用用户的实际任务比较。若当前可用 `hhy-tool-research`，读取该 Skill 的 `references/product-benchmark.md` 建立同任务基线和证据记录。也可以直接按以下步骤准备 DSH 交接。

1. 在 `goal.txt` 放用户目标、任务类型（新项目、既有优化、只做调研）、授权范围、角色、硬约束和验收条件。用 `--context` 给现状、数据以合成样例表示，说明待查假设。选同一任务的现状或最简方案作对照。
2. 用户希望 DSH 自己调研时，在标准任务参数后加 `--explore --independent --workspace <获准取证的目录> --ask-codex` 发原始问题，给选择来源和验证方式的空间。只授权公开调研时，把公开资料或合成样例放在隔离工作目录供其查证。双方各有判断后，用 `--advice` 加 `--benchmark` 传候选或分歧摘录，保留一手入口、版本或查证日期、适用条件和待验项。
3. 把 DSH 的新来源、反例和推断拿回原始说明、代码或实测核对。意见不一致时先统一版本、角色和测试条件。需要集中核对验收漏项时附相关 [质量特性](product-quality.md)，按 [中文交接](model-collaboration.md) 请求必要的证据。
4. 进入正式复查时，用 `--evidence` 传已运行的命令、同任务改前改后结果、反例和未覆盖范围。继续讨论时，把待核实的结果写进 `--context`。区分模型意见与实际验证，记录采用、暂缓或淘汰的理由。只做调研时交代推荐的前提和待验证事项。

`--benchmark` 默认沿用已保存的摘录。后续可传新版，或用 `--clear-benchmark` 撤回，等待桌面接续的请求材料已固定，变化后另发一步。

用[原生独立取证](model-collaboration.md#原生独立取证)核对搜索、读原文、源码读取、命令退出码与结果。判断相同来源能证明什么，把 DSH 自行完成的步骤与 Codex 的复查记入证据。材料型评审可用已有摘录。DSH 真有工具缺口时，再交接必要查证。
