# DSH 桌面接续

交接记录标记 `read_only_investigation: true` 时，只读取证依赖命令行装载的限定工具。沿用原参数取回该命令行会话的结果，或说明缺少实际取证；现有桌面会话无法替代该工具边界。

命令行最终报 `DSH_DESKTOP_REQUIRED` 时使用。自动模式先完成 [WorkBuddy 命令行回退](workbuddy-routes.md)。默认每条线路等待 240 秒，可用 `--timeout` 调整。每次超时先检查命令行输出和已保存的会话，能核实的完整回复直接取回。已有交接文件时，用原参数加交接路线对应的 `--route` 检查原会话是否已完成，这一步不会重新调用模型。仍需接续时再使用 Computer Use。验收命令超时按本机验证失败处理。

等待时可查看本轮 `*.status.md`。超时会尝试结束本轮脚本启动的进程及子进程，再检查结果。若 DSH 桌面未响应，先保留交接记录和其他验证证据，待桌面可用后再决定是否接续。

从会话取回回复时，脚本读取 DSH 的本地压缩会话记录。本流程已验证 DSH Desktop 0.2.2-rc.3 的会话格式。接续前用同一个 Python 环境运行 `python -c "import zstandard"`。如缺少模块，可在允许安装依赖时执行 `python -m pip install zstandard`。常规命令行调用无需此模块。

1. 读取错误给出的 `<步骤>.desktop.json`。其中的 `session_id` 是本任务已绑定的会话，`workspace` 是它原来的目录，`request` 是要核对的请求。旧记录可能只有 `headless_session_id`，可先用它定位原会话。
2. 在 DeepSeek Harness 桌面按原标题或协作记录编号找到会话，复制并核对会话 ID。它可能在「未分组」。等原会话处于空闲，检查最后一轮是否已经完成。无法定位原会话时停在现状，避免再开一条。
3. 如果原会话仍需要接续，按交接记录的 `provider` 和 `model` 选 WorkBuddy 线路，在原会话里只发送一次 `request` 指定的正文。国内 `workbuddy` 在 **WorkBuddy**，国际 `workbuddy-global` 在 **WorkBuddy Global**。遇到登录或工具阻碍，保存现状并说明原因。
4. 等回复完成后，从会话侧栏「… → 复制会话 ID」获取 ID。用原参数（含本轮 `--route`）重跑脚本，在 `--check` 之前加入 `--desktop-session-id <会话ID>`。脚本核对完整请求、工作区、模型来源和完成状态，再导回回复并执行原有验收。可附加 `--desktop-answer <回复文件>` 比对手工保存的文本。
5. 若本地记录还在写入，等当前会话保存后用同一 ID 再试。同一轮导回会绑定首次核对通过的会话和答复。若目标、材料或 Skill 升级后的提示词已变更，用新记录审查当前版本。

命令行和桌面使用同一条会话。已有桌面窗口可能尚未列出另一个进程刚写入的会话，此时先用运行报告的 `session_id` 和日志确认保存情况。仅对升级前已经完成的旧桌面会话保留原导回方式。
